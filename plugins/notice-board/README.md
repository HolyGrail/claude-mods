# notice-board

マシン上で同時に動く Claude Code のセッションへ、リポジトリ単位でお知らせを届ける mod です。
「CI を止めているので Codex のレビューだけ見ればよい」のような状況の変化を、セッションごとに打ち直さずに済みます。

```text
notice 2h: CI is paused, check the Codex review only
notice (all) 1d: Rate limits are tight this week
```

## 使い方

```text
/notice <本文>          同じリポジトリのセッション全体に出す
/notice --all <本文>    リポジトリを問わず、マシン上の全セッションに出す
/notice clear           このセッションの帯に出ているお知らせをすべて消す
```

投稿したセッションが終わっても、お知らせは残ります。
期限はなく、消えるのは `/notice clear` を実行したときだけです。
帯には投稿からの経過時間を出すので、古いお知らせは見ればわかります。

mod が動く Claude Code のバージョンは [usage-meter](../usage-meter/README.md#使い方) と同じです。

### インストール

Claude Code のプロンプトで、次の 3 つを順に実行します。

```text
/plugin marketplace add HolyGrail/claude-mods
/plugin install notice-board@claude-mods
/reload-plugins
```

更新の手順と注意点は、[リポジトリの README](../../README.md) にまとめてあります。

### インストールせずに試す

clone したリポジトリのルートで、次のように起動します。

```bash
claude --plugin-dir ./plugins/notice-board
```

手元のコードを常に読み込むなら、`~/.claude/settings.json` の `env` に `CLAUDE_CODE_PLUGIN_DIRS` としてこのディレクトリの絶対パスを書きます。

## 届き方

各セッションは 60 秒ごとにお知らせを読み直します。
別のセッションで投稿したお知らせは、遅くとも 1 分後には帯に出ます。

モデルには、新しいお知らせを見つけたときに 1 回だけ、会話へ 1 行足して伝えます。
system prompt には書き込みません。
書き込むと、お知らせが変わるたびに prompt cache が無効になるからです。
伝えたお知らせが `/notice clear` で消えたときや、セッションが別のリポジトリへ移って対象から外れたときも、取り下げを 1 回だけ伝えます。
伝えなければ、モデルはもう当てはまらないお知らせに従い続けます。
ただし、同じ本文のお知らせがほかに出ているあいだは、取り下げを伝えません。

投稿したセッションのモデルにも、同じ経路で伝えます。
対話セッションでは、コマンドの出力はモデルが読む会話に入らないからです。

どのお知らせを伝えたかは、会話そのものから読み直します。
mod が足した行を会話の頭から順にたどり、伝えた行と取り下げた行を突き合わせます。
読み直すのは 60 秒ごとと、プロンプトや `/notice` の実行時です。
そのため、会話が入れ替わったり縮んだりしても、いまの会話に合わせて伝え直します。

- `/clear`、コンパクションのあとは、会話に行が残っていないので、いま出ているものを改めて伝えます
- `/resume` や `--resume` で読み込んだ会話には、その会話にない分だけを伝えます。読み込んだ会話で伝えたお知らせがその後消えていれば、取り下げを伝えます
- `/rewind` や復元ピッカーで巻き戻して行が消えたときは、次のプロンプトの前に改めて伝えます
- `/branch` で分けた会話は元の会話の行を引き継ぐので、重ねては伝えません
- mod の再読み込みでは何も失いません。記録を mod の中に持たないからです

`/resume` は新しい会話を mod の受け取るイベントのあとに読み込むので、その間の読み直しが元の会話へ伝えることがあります。
新しい会話には、次の読み直しで伝えます。

## 同じリポジトリの判定

origin の URL を `host/owner/name` の形にそろえて比べます。
`git@github.com:owner/app` と `https://github.com/owner/app.git` は同じリポジトリです。
ホスト名の大文字小文字は区別しませんが、パスの大文字小文字は区別します。パスを区別する Git サーバーもあるからです。
ポート番号も残すので、同じホストの別ポートにあるリポジトリは別物として扱います。
同じリポジトリの worktree も別のクローンも、同じお知らせを受け取ります。
origin がないリポジトリと、origin がローカルのパスや `file://` のリポジトリは、main working tree のパスで比べます。
ローカルの origin は `../upstream.git` のように相対パスで書けるので、綴りが同じでも別のリポジトリを指すことがあるからです。

## ほかの mod からの投稿

`$.store` は mod ごとに分かれていて、ほかの mod からはお知らせのキーを書けません。
ほかの mod は、`/notice` を `$.command.run` で呼んで投稿します。

```js
await $.command.run({ command: 'notice', args: 'main advanced (#12). Rebase before the next push.' })
```

pr-relay（#4）がマージを検知したときに「main が進んだ」と出すのは、この形を想定しています。
文面には、次の push の前に rebase するよう書くことを勧めます。
作業の途中で rebase すると、コンフリクトの解消が実装の変更と混ざるからです。
`$.command.run` はセッションが待機中になってから実行されるので、投稿は数分遅れることがあります。

## 制約

`$.store` には atomic な更新がないため、お知らせごとに `notice:<id>` のキーを分けています。
投稿がほかのお知らせを上書きすることはありません。
ただし、`/notice clear` の実行中に投稿されたお知らせは、消えずに残ることがあります。

伝えたかどうかは、お知らせの範囲（リポジトリかマシン全体か）と本文で見分けます。
範囲と本文が同じお知らせが二つ出ていても、モデルには 1 回だけ伝えます。
`$.session.messages()` が返すのは新しい 4096 件までなので、それより前に伝えた行は会話にないものとして、もう一度伝えます。
伝え直した行は新しい側に入るので、取り下げが漏れることはありません。

モデルへの伝達が拒否されたとき（プラグインが会話を変えられない実行や、上位のプラグインによる拒否）は、同じ会話のうちは再試行しません。
どちらも次の試行で結果が変わらないからです。帯には出たままになり、伝えられなかった行は debug ログに残ります。
会話が入れ替わったり巻き戻しで縮んだりしたとき、および mod の再読み込みのあとは、一度だけ試し直します。

## テスト

```bash
cd plugins/notice-board
claude plugin test
```

テストキットでは、mod の `$.session.append` がテストのフックに届かず、失敗します。
append が失敗すると、mod はモデルに伝えられなかった行を debug ログに残すので、テストはその行でモデルに渡す内容を確かめています。
テストの `$.session.messages()` は、その行を会話に足した形で返します。`/clear`、`/resume`、`/rewind` は、テストが会話を入れ替えて再現します。
