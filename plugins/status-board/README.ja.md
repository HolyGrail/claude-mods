# status-board

[English](README.md) | 日本語

このセッションがいま何を目指し、どこまで進み、何を人に聞いているかを、会話の横の枠（Pane）に「状況ボード」として出す Claude Code の mod です。
いまの状況を 1 行で、プロンプト入力欄の上の帯にも出します。

```text
● 進行中 (3/6) 帯を描く · 23:41  [ 状況ボード ]
```

長いセッションでは、いま計画のどこにいて、最後に何を頼み、何が決まったかが、会話をさかのぼらないと分からなくなります。
会話にはツールの出力や応答の本文も積もるので、指示や決定はその間に埋もれます。
状況ボードは、その会話全体をモデルに要約させたものです。
要約の元になった記録は、ボードの下に指示ごとの履歴として畳んであります。

## 状況ボード

ボードは、次の 5 つの見出しを持つ Markdown です。

```text
## 目的
- 帯と枠でセッションの流れを見せる
## 未解決・あなたの判断待ち
- README の書き直しを、この PR でやるか、次の PR に回すか
## 現在地
- 帯の色を直し終えた（テスト実行で確認）
- いまは枠を、指示ごとのカードで見せる形に作り替えている
## 決まったこと
- ボードは会話ログから組み立てる。途中から有効にしても組み直せるため
## 次の一手
- モデルがテストを直し、そのあと README に移る
```

モデルには、会話を読んでいない人に向けて書かせます。
ボードだけを読んで、会話に戻らずに状況と自分が決めることをつかめるようにするためで、短くすることは狙っていません。
会話の中で付いた呼び名（案の名前、作業の通称）や PR・issue の番号は、それだけでは書かせません。何をするものかを先に書き、呼び名や番号は括弧で添えます。
1 項目には 1 つのことを 1〜2 文で書かせ、1 項目の字数に上限はありません。
上限があるのはボード全体で、およそ 1,200 字（英語は 2,000 字）です。
超えそうなときは項目の中身を削らず、項目の数を減らします。判断待ちの項目は最後まで残します。

ボードの `（#12）` のような PR 番号は、このセッションが紐づけた PR（履歴に並ぶ PR）であれば、クリックで開けます。
リンクを付けるのはモデルではなく mod で、ボードを描くときにトランスクリプトの URL から付けます。
モデルに URL を書かせると、存在しない URL を書くおそれがあるからです。
そのため、セッションごとに保存するボードはモデルが書いたままです。
`ボードをコピー` でコピーされるのは、リンクを付けたほうです。
次の番号はリンクにならず、文字のまま残ります。

- その番号の PR を、このセッションが紐づけていない
- 別々のリポジトリから、同じ番号の PR を 2 つ紐づけた
- URL が `https:` でない
- コード（バッククォートやフェンス）か、既存のリンクの中にある
- URL や語の一部になっている（`issues/12#3`、`abc#12`。`#123` は `#12` とは別の番号として扱う）

ボードの下には、`HH:MM 時点 · モデルによる要約` の 1 行が付きます。
ボードを書いたあとに出来事があったか、ターンが終わっていれば ` · その後に動きあり`、かかったトークンが分かれば ` · 読み 323k / 出力 490` が続きます。
ボードはモデルの要約なので、言い回しや取捨はモデルしだいです。
元の記録を確かめたいときは、`履歴を表示` で指示ごとのカードを開きます。

### いつモデルを呼ぶか

要約は、セッションの会話を引き継いだモデル（`$.model.fork`）にツールなしで 1 回答えさせて作ります。
このモデルには、終わったばかりのターンの最終回答まで見えています。
人の判断を待つ問いは最終回答に書かれることが多く、ターンの終わりの要約でボードの判断待ちにそのまま載ります。
呼ぶのは次の 3 つの場合だけです。

- **ターンが答えて終わったとき**：枠が開いて表示されていれば要約し直す。閉じている間や、置けなかった枠のためには呼ばない
- **枠を開いたとき**：枠が置けて、ボードがないか古く（`その後に動きあり` の状態）、しかも会話のキャッシュがまだ温かいと見なせるときだけ要約する。温かいと見なすのは、ターンの実行中か、最後のターンが終わってから 5 分以内
- **ボタンを押したとき**：`状況ボードを作る` か `状況ボードを更新する` で、いつでも要約する。キャッシュが温かいと見なせないときは、ラベルに `（キャッシュ切れの可能性あり）` を添える

要約は同時に 1 つしか走らせず、その間のボタンは `要約しています…` になり、押しても何もしません。
その間にターンが終わると、走っている要約にはその回答が入っていない可能性があるので、終わってからもう一度だけ要約します。
失敗したときは前のボードを残し、ボタンの下に `要約できませんでした: <理由>` を出します。
ボードはセッションごとに保存し、再起動や `/resume` のあとはそのまま戻します。
`/branch` で分かれた会話は、ボードなしから始めます。
8 日間書かれていないボードは消します。

### コピー

Desktop アプリでは枠の文字を選択できません。mod の側から選択を許す手段もありません。
そこで、`状況ボードを更新する` の横のボタンでクリップボードに入れます。
`ボードをコピー` は表示中のボードを Markdown のまま、`履歴をコピー` はすべてのカードを新しい順にプレーンテキストでコピーします（表示を絞っていても全件）。
履歴の指示とまとめは保持している文面のまま入るので、保持の上限（まとめは 1,000 文字、ほかは 200 文字）を超えた部分はもう切れています。
コピーできたかどうかはトーストで伝えます。

### 校正

ボードの文面には、AI が書く文章に特有の語彙や言い回しが出ることがあります。
その直し方は人によって違います（校正のスキルを使う人もいれば、自分の規範を持つ人もいる）。
そこで mod は 1 つの流儀を決めず、利用者が指定した規範を、出来上がったボードに 2 段目として当てられるようにしています。
既定では何もしません。設定しなければ、以下のことは起きず、費用も変わりません。

設定は 2 つです。

| 設定 | 内容 | 既定 |
| --- | --- | --- |
| `proofreadRules` | 規範のファイルのパス。スキルの `SKILL.md` でも、自作の Markdown でもよい。先頭の `~/` はホームフォルダ。フォルダを指したときは、その中の `SKILL.md` を読む | 空（校正しない） |
| `proofreadModel` | 校正に使うモデル。別名（`haiku`、`sonnet`、`opus`）か、モデル ID そのもの | `sonnet` |

plugin に入っているスキルは、パスに plugin のバージョンが入り、更新のたびに変わります。
そのため、パスの 1 区間まるごとを `*` にできます。mod がそのフォルダを列挙し、バージョンが最も新しいもの（`3.9.0` より `3.10.0`）を選びます。

```text
~/notes/writing-rules.md
~/.claude/plugins/cache/<marketplace>/<plugin>/*/skills/<skill>
```

設定する場所は、Claude Code が plugin の設定を持つところです。
インストール時の設定画面か、ターミナルの `/config` の行で変えられます。
settings.json なら `pluginConfigs` の下に、plugin ごとのキーで書きます。次の例は `--plugin-dir` で読み込んだときの形で、キーは `status-board` です。インストールした plugin のキーの綴りは、まだ確かめていません。

```json
{ "pluginConfigs": { "status-board": { "options": { "proofreadRules": "~/notes/writing-rules.md", "proofreadModel": "sonnet" } } } }
```

起きること:

- 要約は届いた時点ですぐ表示します。2 段目の間、ボタンは `校正しています…` になり、校正後が届いたら差し替えます
- 2 段目は、会話を読まない単発の呼び出し（`$.model.complete`）です。渡すのは、mod が持つ固定の枠の指示、規範のファイルの文面、ボードの 3 つです。枠の指示は、見出し、項目の数と順序、事実、数値、固有名、括弧の中、バッククォートのコードを変えず、言い回しだけを直して、校正後の Markdown だけを返すよう求めます。枠と規範は先頭に置き、キャッシュに載せます
- 返ってきた文面は機械的に確かめます。5 つの見出しが要約と同じ順で並び、箇条書きの項目数も同じでなければ、校正後は捨てます
- 校正後を表示している間は、ボードの下の行に ` · 校正済み` を足し、トークンは 2 段の合計を出します。`校正前を表示` で要約のままのボードに、`校正後を表示` で校正後に戻ります。`ボードをコピー` は表示中のほうをコピーし、どちらをコピーしたかをトーストで伝えます（`校正後のボードをコピーしました。` か `校正前のボードをコピーしました。`）。校正前後の差が読点数個だけのこともあり、画面では見分けにくいためです
- 規範のファイルが読めない、200 KB を超える、モデルが答えない、検査に落ちる、のどれかなら、要約のままのボードを残し、ボタンの下に `校正できませんでした: <理由>` を出します。要約そのものの失敗とは別に出ます
- ボードは、校正が済んだ時点で両方の文面を保存します

制約:

- 規範のファイルは、従うべき文面として渡します。スキルを実行するわけではありません。そのため、ツールを使う手順や、別のファイルを参照する指示は働きません
- 規範はボードの更新のたびに送ります。規範が長いと、そのぶん毎回の時間とトークンが増えます（5 分以内ならキャッシュした部分は安く済みます）
- 意味を変えないための守りは、枠の指示と、見出しと項目数の検査までです。項目の中の言い回しが意味ごとずれても、機械的には防げません。気になるときは `校正前を表示` で見比べてください

### コストの目安

要約はメインの会話のキャッシュを読むので、温かいうちなら安く済みます。
Desktop アプリで測った 1 回は、5.9 秒、キャッシュからの読み 321,578 トークン、新たな入力 1,063 トークン（うち 685 トークンはキャッシュへの書き込み）、出力 490 トークンでした。
キャッシュが切れたあとは、会話全体を通常の入力として読み直すので、その分だけ高くつきます。
枠を開いたときにキャッシュが冷えていそうなら自動では呼ばず、ボタンを待つのはそのためです。
`effort` は渡さず、急いで答えるようにだけ頼んでいます。
セッションと違う `effort` を渡すと、モデルによっては会話全体をキャッシュに書き直すことになるからです。

## 帯

進行中のステップがあれば、`進行中` と計画の中での位置（`(3/6)`）、ステップの名前、そのステップが始まった時刻を出します。
なければ、最新の出来事を 1 件、次の形で出します。

| 印 | 種類 | 本文 |
| --- | --- | --- |
| ●（緑） | ステップの完了 | `完了 <ステップ>` |
| ●（青） | ステップの開始 | `進行中 <ステップ>` |
| ○（灰） | ステップを未着手に戻した | `未着手 <ステップ>` |
| ●（青） | 計画の作成と更新 | `計画を作成: N ステップ`、`計画を更新: N ステップ` |
| ○（橙） | まとめ（`wrap_up`） | `まとめ <本文>`、質問があれば ` ／質問: <質問>` |
| ●（橙） | 質問（`AskUserQuestion`） | `質問 <先頭の質問>`、複数なら `（ほか N 問）` |
| ○（紫） | 人の指示 | `指示 <本文>` |
| ○（青） | PR の紐付け | `PR #12 を紐付け` |

行末の `状況ボード` ボタンと `/board` コマンドで枠を開閉します。
出来事がまだないときは何も出しません。
ターミナルでは幅に収まるようステップの名前や本文を切り詰め（`進行中 (3/6)` は残す）、それでも収まらなければ行ごと出しません。
ほかの mod の行とは別の行に描きます。

## 履歴

`履歴を表示` を押すと、ボードの下に、人の指示 1 件と次の指示までに起きたことを 1 枚にしたカードが並びます。
Desktop アプリでは枠の行から会話のその位置へ飛べないので、カードは枠の中だけで読み切れるように作ってあります。

```text
○ 23:20 帯の表示を直して
○ 23:38 帯の色を直し、時刻を薄くした。テストは通過。
質問: README も直しますか?
● 進行中 (3/6) 帯を描く
計画 6 ステップ · 完了 2 · PR #12
```

カードの中身は、上から次のとおりです。

- **見出し**：指示の時刻と本文。本文は 3 行まで折り返す
- **まとめと質問**：起きた順に並べる。まとめは全文を折り返して出し、まとめに質問が付いていれば、その下に `質問: <質問>` を警告色で出す。`AskUserQuestion` は `質問 <先頭の質問>` の形で、これも折り返して出す
- **進行中の行**：計画に進行中のステップがあれば、いちばん新しいカードにだけ、帯と同じ `進行中 (k/N) <ステップ>` を出す
- **足元**：そのカードの間の計画とステップを畳んだ 1 行。最後に出た計画のステップ数、完了したステップの数、紐付けた PR を ` · ` でつなぐ

タスクの通知やほかのセッションの入力で始まったターンのまとめは、直前の指示のカードに入ります。
最初の指示より前の出来事は、`最初の指示より前` という見出しのカードにまとめます。

カードは新しい順に並べ、最初は 5 枚を出します。
`さらに N 件を表示` で全部に、`新しい 5 件だけにする` で戻ります。
Desktop アプリではカードを枠線で囲み、ターミナルでは 1 行あけて区切ります。
Desktop アプリで枠を最小化した小さな形では、ボードではなく、いちばん新しいカードの最新のまとめ（なければ指示）を 3 行まで出します。

色はテーマの色に従います。
時刻は今日の出来事なら `HH:MM`、それより前なら `M/D HH:MM` で、マシンのタイムゾーン（`TZ` に `Asia/Tokyo` のようなゾーン名があればそのゾーン）で表示します。
まとめと質問は 1,000 字、ほかの本文は 200 字で切り、出来事は新しい 300 件まで覚えます。

人の指示として数えるのは、ターンを始めた入力のうち、人が入力したと記録されたものだけです。
plugin、タスクの通知、ほかのセッションが差し込んだ入力（`promptSource` が `system` のもの）は数えません。
Claude Code が入力に添える `<system-reminder>` の部分は本文から除き、それしか残らない入力は数えません。

## どのセッションで何が出るか

状況ボードは会話そのものを要約するので、どのセッションでも作れます。
履歴と帯に出る出来事は、セッションを動かしているアプリで変わります。
計画、ステップ、まとめの元になる `mcp__ccd_turn__update_plan` と `mcp__ccd_turn__wrap_up` は、Desktop アプリのセッションにしかないツールです。

- **Desktop アプリのセッション**：「帯」の表にある出来事がすべて出る
- **ターミナルのセッション**：指示、質問、PR の紐付けだけが出る。カードには見出しと質問と、足元の PR だけが載る
- **`claude -p` の実行**：入力が人の指示として記録されないので、指示も出ない

人の入力の記録のされ方は、直近 14 日の会話ログで確かめました。
Desktop アプリでは `promptSource` が `sdk`、ターミナルでは `typed` か `queued` で、どちらも `origin.kind` が `human` です。
`claude -p` の入力は `promptSource` が `sdk` でも `origin` がないので、指示として数えません。

## 仕組み

出来事は、フックで積むのではなく、セッションの会話ログ（JSONL）を読んで組み立てます。
決め手は計画のステップでした。
ステップの状態は、`update_plan` の入力（一覧の置き換え、`advance`、`done`、`start`）をそれまでの計画に順に当てはめないと分かりません。
フックだけで積むと、`/resume` した会話や、途中で mod を有効にしたセッションでは、それまでの計画を組み直せません。
過去の出来事の時刻と、入力が人によるものかどうかも、会話ログにしか書かれていません。

会話ログは前回読んだ位置から先だけを読みます。
読み直すのは、ターンの開始の少しあと、ターンの完了時、ターンの実行中は 2 秒ごと、待機中は 30 秒ごとです。
どの読み込みもターンを待たせません。
`/resume`、`/clear`、`/branch` で会話が切り替わると、新しい会話のログを先頭から読み直します。
読み込みが 3 回続けて失敗すると、ステータス行に `status-board: 会話ログを読めません: <エラー>` と出し、次に読めたところで消します。
会話ログがまだ作られていない間（セッションの最初の入力まで）は、失敗に数えません。

組み立て方は、ローカルのダッシュボード agent-dashboard の会話ログの読み取りから移植しています。

## 表示言語

status-board の文言は、既定では英語です。
Claude Code の `language` 設定が日本語を指していれば（`ja`、`jp`、`jpn`、`japanese`、`日本語`、または `ja-` か `ja_` で始まる値）、日本語に切り替わります。
`language` 設定がないときは、環境変数 `LC_ALL`、`LC_MESSAGES`、`LANG` のうち最初に値のあるものが `ja` で始まれば（`ja_JP.UTF-8` など）日本語です。
`language` にほかの値を書いた場合は、環境変数にかかわらず英語になります。

```json
{ "language": "japanese" }
```

切り替わるのは、画面に出る文言（帯、枠、そのボタンとラベル、`/board` コマンド、トースト、ステータス行）と、モデルに送る文言（要約のプロンプト）の両方です。
そのため、ボードも見出しから箇条書きまでその言語で書かれます。
以前に保存したボードは、次に更新されるまで、書かれたときの言語のまま表示します。
言語はセッションの開始時に決めるので、設定を変えたときは、次のセッション開始か plugin の再読み込みから反映されます。
時刻は、どちらの言語でもマシンのタイムゾーン（`TZ` に `Asia/Tokyo` のようなゾーン名があればそのゾーン）で表示します。

この README に引いた表示やボードの文面は、日本語を選んだときのものです。
英語の文面は[英語の README](README.md) に載せています。

## 使い方

確かめてあることと、まだのことは次のとおりです。

- **Desktop アプリ（エンジン 2.1.326）で確認**：帯の表示。枠がウィンドウ右端の列に出ること。ボタンの押下からの要約 1 回（5.9 秒、キャッシュからの読み 321,578 トークン、出力 490 トークン）
- **Desktop アプリ（2.1.326）でのコピー**：試作 mod のボタンから呼んだ `$.ui.copy` は `isCopied: true` を返した。この mod のコピーボタン自体は、まだ押して確かめていない
- **`claude -p --plugin-dir`（v2.1.327）で確認**：mod の読み込み（フックの受け付けと `/board` の登録を含む）。会話ログの読み取り（33 MB の会話ログを最後まで読み、件数が別の方法で数えた値と一致した）。`turn.complete` のフックから頼んだ要約が返ること
- **Desktop アプリ（2.1.326）での PR リンク**：試作 mod の枠の `Markdown` に `[#55](https://github.com/owner/repo/pull/55)` と書いたリンクが描かれ、クリックするとブラウザで開いた。続いて、この mod のボードに出た `#56` のリンクも、クリックするとその PR が開いた。ターミナル（型定義では OSC 8 のリンクとして描かれる）は試していない

`/plugin` でのインストールと更新の手順は、[リポジトリの README](../../README.ja.md) にまとめてあります。
インストールせずに試すときは、clone したリポジトリのルートで次のように起動します。

```bash
claude --plugin-dir ./plugins/status-board
```

## 制約

- 会話ログを持たないセッション（`$.session.info()` の `transcriptPath` が空）では何も表示しない
- 1 行が 64 MiB を超える会話ログの行（大きな画像を貼った入力など）は読み飛ばす。その行が人の指示でもカードにならない
- 初回は会話ログを先頭から読むので、長いセッションではカードがそろうまで少しかかる
