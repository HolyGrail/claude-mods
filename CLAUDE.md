# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A collection of Claude Code mods: plugins under `plugins/<name>/` whose hooks are function hooks (a JS module exporting `register(on)`), listed in `hooks/hooks.json` under `"modules"`. The repo root is also a plugin marketplace: `.claude-plugin/marketplace.json` lists every plugin, so a new plugin needs an entry there, and a user-visible change should bump `version` in that plugin's `plugin.json` so `claude plugin update` treats it as a new release. There is no package.json or build step; the module runs as plain JS inside Claude Code. The plugins are `plugins/usage-meter`, `plugins/pr-relay`, `plugins/notice-board` and `plugins/zsh-safe`.

User-facing docs (README.md) are written in Japanese; code comments, commit messages and test names are in English.

## Commands

Run from each plugin's directory (e.g. `plugins/usage-meter`):

```bash
claude plugin test               # runs every *.test.ts / *.test.tsx under the folder; exits 1 on failure
claude plugin validate .         # checks the manifest and lists the hooks and $ APIs the module uses
npx -y -p typescript tsc -p .    # type check (no TypeScript in the repo; npx fetches it)
```

To try the mod in a live session, run `claude --plugin-dir ./plugins/usage-meter` from the repo root.

`tsconfig.json` extends `.claude-plugin/types/tsconfig.json`, which holds the `claude-code` type declarations; that `types/` directory is not in git. The config has no `checkJs`, so `tsc` checks only the tests: `hooks/register.js` itself is never type-checked, and `claude plugin validate` is the only static check on it.

## Testing approach

Tests import `test`, `expect` and `mock` from `claude-code/testing`. Each test gets `$` (drives events into the module: `$.session.start`, `$.session.measure`, `$.tool.call`, `$.ui.mount`, …) and `on` (stubs the host side: `session.usage`, `session.id`, `store.*`, `process.run`, `fs.*`, `prompt.submit`, `ui.render`). `mock.clock(on, { now })` fixes time. Shared helpers `stubSession` / `stubStore` back `$.store` with a `Map` so tests can assert on, or pre-seed, what other sessions saved. Assertions find rendered nodes with `ui.find({ type, text })`.

## usage-meter architecture

`hooks/register.js` draws a band above the prompt (`ui.render` for `AbovePrompt`) with meters for context, the 5-hour limit and the 7-day limit. It always calls `next(e)` and stacks its line above whatever later mods draw.

State lives in module-level variables, which may survive a re-fired `session.start` (enable or worker respawn), so `session.start` resets them and cancels the previous ticker.

Rate limits are per account, so readings are shared across all sessions on the machine through `$.store`, and that sharing is the subtle part:

- Each session writes only its own key, `reading:<sessionId>`, holding `{ at, limits }`, because `$.store` has no atomic update. Every session displays the newest reading among all keys (`scan`), with ties broken by key so all sessions agree.
- At startup, a shared reading always wins over `$.session.usage()`'s snapshot; the snapshot is saved only when no shared reading exists.
- A 60 s ticker (`$.clock.every`) re-scans the store and refreshes countdowns and time markers.
- Key cleanup: on a final `session.end` (`prompt_input_exit` / `other` only; `/clear`, `/resume` and logout keep running), a session deletes its key unless it holds the newest reading, in which case it marks it `ended: true` so others may delete it once something newer exists. `prune` also deletes non-readings and anything older than `STALE_MS` (8 days).
- `/clear`, `/resume` and `/branch` (fork) switch session id mid-module, handled in `classic.SessionStart`: the old key is released as if ended and writes move to the new id. Compaction keeps the same key.

Rendering: SVG gauge when `e.surface === 'desktop'`, otherwise a text bar sized against `props.bodyColumns` (dropped entirely when the line won't fit). Color rules and thresholds are in the README and the constants at the top of `register.js`.

## notice-board architecture

`hooks/register.js` answers `/notice` (registered in `session.start`), stores each notice under its own key `notice:<postedAt>-<sessionId>-<count>` holding `{ text, repo, postedAt }`, and draws the newest three above the prompt. `repo` is null for `--all`; otherwise it is the origin remote normalized to `host[:port]/path` (URL and scp-style spellings alike, bracketed IPv6 hosts included, host lowercased, path case kept; `path:<main working tree>` with no remote or a local one, whose spelling may be relative), so every worktree and clone of a repository matches.

- A 60 s ticker re-reads the store, and so do every `prompt.submit` and `/notice`. What the model was told is read back from the conversation (`$.session.messages()`): one user row per notice or withdrawal, whose whole text is `Notice to every Claude Code session …` or `This notice no longer applies: …` (never split on new lines, so a body may hold anything) and ends with `(notice-board ref <8 hex>)`, a SHA-256 of the body under a machine secret kept in `$.store` (`secret:<hex>`, one key per secret so sessions that make one at once each keep theirs; rows are signed with the first by key and accepted under any), so a prompt that only reads like a row is ignored; walked in order, keyed by scope and text. Because a full 4096-message window can drop old rows, each conversation's told notices are also kept in `$.store` as `told:<sessionId>` (`{ at, told: [{ key, text }] }`), so a cleared notice whose row a full window dropped or a compaction folded away is still withdrawn (the record only adds withdrawals: a notice still shown whose row is gone is told again); records not written for 8 days are pruned at `session.start`. Notices the conversation lacks are appended with `$.session.append`; ones it holds that are no longer shown here (cleared, or for a repository the session left) are appended as withdrawn, unless a notice still shown carries the same text. The posting session is told too: a command's output is not what the model reads. Nothing is written to `$.state`: version 0.1's `notice-board.known` is only read at `session.start`, to accept that version's unsigned, newline-joined rows whose text it lists (`partsV1` takes a listed body whole, longest first, so a body holding a line-like new line isn't split), so an upgraded session still withdraws what was cleared (the contract stays in `types/index.d.ts` for that read). So a reload, `/clear`, compaction, `/resume`, `/rewind` and `/branch` all reconcile against whatever conversation is installed; a tick that lands on the outgoing conversation during `/resume` is healed by the next load. A refused append is remembered in a module `Set` and not retried until `session.start` or `classic.SessionStart` clears it (bumping `generation` before and again after the switch, so a load begun before or during it doesn't refill it or write the record). `classic.SessionStart` takes the new `sessionId` only after `next(e)`, and each load keeps the id it started with, so a tick during the switch keeps the outgoing conversation's record to it; along with the id it starts re-reading 0.1's `$.state` for the new session (`legacy` is that read's promise, which each load takes with its id, so a tick never pairs the new conversation with the old record) and, on a fork, merges `told:<old>` into `told:<new>` in the load queue (a tick under the new id may already have written a record from its window), or the conversation stops carrying on from the one the refusal was met in (`continues` compares message fingerprints, allowing for the oldest dropping out of the 4096-message window).
- Every load goes through one queue (`refresh`), so a tick and a command can't tell the model twice. The queue survives a re-fired `session.start`, and a final `session.end` cancels the ticker.
- Other plugins post with `$.command.run({ command: 'notice', args })`, since `$.store` is per plugin.
- The test kit never routes a plugin's `$.session.append` to the test's hooks; the call fails, and the mod logs the untold lines to the debug log, which the tests read through a `ui.log` stub.

## pr-relay architecture

`hooks/register.js` polls the session's pull request every 60 s with one `gh api graphql` query (`$.process.run`) and wakes the session with `$.prompt.submit` when Codex reviews or approves it; a merge raises a toast and a `cleanup` button in the band instead, and a merged or closed pull request stops the polling. CI is left to the desktop app.

- The pull request comes from `gh pr view` for the checked-out branch, the URL a `gh pr create` Bash call printed, or `pr_url` passed to `mcp__pr-relay__watch`.
- In the desktop app, `$.tool.list()` detects `mcp__ccd_pr__get_status` once per conversation and `$.tool.call()` reads its cache at discovery and on a separate minute timer. An open primary takes precedence over `gh pr view` at startup; later only a change of primary URL takes over the watch, leaving explicit watches intact until then. Other bound pull requests, including a primary outside the watch, are tracked by state in this conversation: an observed open-to-merged or open-to-closed transition raises a toast, and a merge adds to the same cleanup offers list as the watched pull request. The band shows the newest three offers with independent cleanup and dismiss buttons; changing the watch removes only the new watch's own offer. Tool failures preserve the gh path, reads from an older generation cannot act, and conversation switches reset desktop availability, the last primary, bound states and offers. The desktop timer survives watch changes and merges, but is replaced on conversation switches and cancelled on a final session end.
- Codex events count only after the last push (the newest of the watch tool's `since` or the start of `gh pr create`; the start of a `git push` this session ran, once the head has moved, or a push another session's poll note carries; and the head commit's date). Nothing is relayed while a `git push` runs. Each connection is followed back a page at a time while its oldest item is still after the last push: Codex's thumbs-up is one reaction per pull request whose time can stay at an older push. The rules are ported from the skill's `poll-codex-review.sh`; the GraphQL login has no `[bot]` suffix.
- Unrelayed reviews come before an approval. A newer approval is marked with them: one after the newest review is mentioned at the end of the review prompt, and an earlier one is superseded silently. At delivery, after the record write and outside the write queue, one extra `nodes(ids:)` query fetches exactly those reviews and up to 100 inline comments each; the polling query carries review node ids but no review or inline comment bodies. The prompt lists comments oldest review first, with each body capped at 4,000 characters and the whole prompt at 30,000, linking to the pull request's files page for omitted comments. A review without inline comments contributes its body with `<details>` blocks removed. A failed or unusable details response still wakes the session with counts, the pull request URL and a `gh api repos/<owner>/<name>/pulls/<number>/comments` fallback. Fetching and submitting never hold up the poll, and a prompt that does not enter takes back both marks it made without undoing a newer approval.
- `/resume` can switch the conversation without a new `session.start`, so `classic.SessionStart` with `source: 'resume'` drops the watch and looks for the pull request again. `/clear` and `/branch` (fork) go the same way, since they too move the conversation to a new id: the note under the last id is left idle and the cached id is asked again.
- Polls run on `$.clock` timers, never inside a hook: a prompt `$.prompt.submit` queues resolves only when its turn starts, so awaiting one inside `tool.call` would wait on the running turn. `generation` lets a poll or lookup started before the latest watch or stop leave the state alone.
- What was relayed is kept per pull request under `pr:<id>` (the URL in lower case) in `$.store`, so a second session on the same pull request, or a restart, is not woken again. The record is marked before the prompt is sent, and a prompt that did not enter (rejected, or dropped by a hook) takes its mark back for the next poll to resend. The merge or close toast and the usage-limit toast go the same way: raised only once the record says so in time and no push came meanwhile, and otherwise taken back (a merge or close taken back keeps the pull request polled, so a later round tells it); a take-back the store refuses is shown in the status line.
- Sessions polling the same pull request at the same moment would each read the record before the other wrote it, and `$.store` has no atomic update. So each poll first writes the session's own `poll:<sessionId>:<id>` note `{ pr, at, since, pending?, running?, idle?, deferred? }` (`since` holding the last push the session knows of; `pending` the `git push` calls it ran that have not counted yet, each `{ id, at, head, shas?, running? }` tracked on its own by its `id` (parallel pushes do not overwrite each other, even ones started in the same millisecond) with the head as lately known when the push started (its own last poll, or the record's head when another session saw it later; none when the record holds another head seen in the same millisecond as its own; with neither, the pushing session falls back on the record's head only if GitHub showed it before the push started: `record.headAt` and the session's own are the times GitHub answered the first page, not when the polls started or the older pages came), written as the push starts, and once it finishes the commits its output says it pushed (`Everything up-to-date` drops the push, unless another push in the same Bash call printed an update); the relaying session applies it once it has finished and GitHub's head is one of `shas` and not `head` (another ref moved to the commit the head already was), the one the pull request's own branch moved to when the output names branches (another branch pushed to a commit the pull request reached by itself is not its push), or, when the output named none, differs from `head`; with no head known before it, a push counts only once its output shows the pull request's own branch (`headRefName`) moved to GitHub's head (each push keeps `refs`, the commit each branch moved to, read from the usual output or `--porcelain`'s), and otherwise stays pending, for the pushing session too; a finished push also keeps `doneAt`, and a push, this session's or another's, that has not counted and finished at or after the millisecond GitHub answered (or, with no `doneAt`, started then) holds the relay back for that poll, since the head GitHub showed may be the one it replaced; `at` is read just before the note goes out, once the session id is known; a push's own `at` is read again just before its Bash call runs (after its last note went out; that time goes to the notes as the call starts, without waiting on the store), since Codex activity while its notes went out is still about the old head), and after the GitHub query (far slower than a store write) yields to any earlier note for the same pull request from the 30 s before it, or up to 10 min before it while still `running` (a tie goes to the smaller key), or to a later one, or one timed in the same millisecond, written while its own note was still on its way to the store (both may then yield, and the next round relays), unless that note is `deferred` (it yielded itself, which it writes before reading the record, and polls a few seconds apart would otherwise yield round after round with none relaying): it then relays nothing and never writes the record, whose copy it read may predate the leader's marks; a push it knows of goes into its note's `since` instead, which the relaying session folds into the record's baseline. A poll overtaken by a new watch before its note goes out writes nothing, and only a poll that wrote the record moves `pagedAt`. A session runs one poll at a time (`polling`), so a tick during a slow query cannot overwrite the note of the round still in flight. A poll drops `running` from its note once it has written the record. Notes are per pull request, so a session that turns to another leaves the last one's push behind. A failed query, a final `session.end`, a re-fired `session.start`, `/resume` and a switch to another pull request leave the note `idle` instead of deleting it: it takes no part in the election, but its `since` still counts. A new watch leaves the stopped poll's note idle as it starts, not at its first poll; watching the same pull request again keeps the baseline that note held. A leader that dies before relaying no longer holds anyone back on the next round, and a poll that reaches 30 s short of that 10 min (checked when GitHub answers, after reading the notes and again just before writing the record) relays nothing, since another session may have taken the round over. An ended poll that finishes after the watch turned leaves the next pull request's baseline, pushes, note and status alone, and writes its own record with the baseline its note held. A poll whose note cannot be written does not query at all, one whose deferral the store refuses stops as failed, and one that cannot read the other notes relays nothing; both show the failure in the status line. While a `git push` runs, its `pending` carries `running`, and every other session relays nothing either (for up to 10 min after the push started), since GitHub may still show the head being replaced. A push is bound to the pull request watched as it starts, and one started before that pull request had a note (its first poll not having written one yet, or the watch turned away) gets an idle note of its own, which that first poll takes up. A push is bound, and counted as started, before anything is awaited and goes out running before its head is looked up (the session id is cached from `session.start` and asked again on `/resume`, so a push before the first note does not wait on it; a push whose watch turns while it starts stays out of the next pull request's pushes, as does one still pending for a pull request that ended; only a push made while none was watched carries over to the pull request found next, which then keeps it), and again with the head. Only the pushes bound to the watched pull request hold this session's relays back (a running one for up to the same 10 min as another session's, so a hung Bash call does not hold them back for good; past that it is taken as finished with nothing known of what it pushed, and counts once the head moves), including one that started after the poll asked GitHub, running or already done: its marks are taken back. So does a push, or a newer `since`, another session's note shows once the record is written that it did not show when the notes were read, or a push it showed that has finished since (even one past its hold); the notes are read once more after the lease is checked, so a push started while the clock was read counts too; a poll whose read of them lands past the lease sends nothing and takes its marks back, since the session that took over read them and sent nothing either. A record write that lands past the lease sends nothing, since a session that took the round over may have relayed the same; `$.store` has no conditional write to keep it from landing. Its marks are taken back, so a later round sends what nobody did. A record that cannot be read as the push starts leaves its head unknown, and a Bash call that throws still marks the push finished in the note. Writes to a note go out one at a time, each taking the note's value when it goes out, so a write the store answers late never lands over a later one. A note left idle is rewritten until the store has taken it as idle and with its pushes as they stand (a running push finishing, with the commits it pushed, even after the session turned to another pull request); a refused write is retried at the next poll, and coming back to a pull request takes the pushes and `since` its left note still held, and a module started afresh for the same session (a worker respawn) takes them from the note it finds in the store under its own key, its pushes as finished (one still running there keeps holding the relays back for the same 10 min, since only the worker went); a push note the store will not take is shown in the status line rather than holding up the push; and each poll carries a `serial` so one cut short by a restart never marks its successor's note finished. A deferring session leaves a merge or close to the leader too (no toast, no stop, no cleanup button) and picks it up from the record on a later round. `prune` drops this session's own notes that it no longer holds after an hour once the `pr:` record's `since` covers their `since` and `pending` (others of its own stay until `STALE_MS`), queued behind any write to the key still going out, and checked again once those are out in case a watch took the note up meanwhile. Another session's note is dropped only once older than `STALE_MS` and only when its pull request's record is ended or gone: `$.store` has no conditional delete, so a note that session rewrote between the read and the delete would vanish from the election, and a session polling a pull request rewrites its note every minute.
- A startup `prune` the store fails does not stop the lookup.
- A `gh pr view` lookup that fails (not "no pull requests found") shows `PR 検索失敗 HH:MM: <error>` in the status line while it is retried each tick.
- The tool `mcp__pr-relay__watch` is how the skill tells the mod runs (and can set the pull request and baseline).

## zsh-safe architecture

The zsh options come from `zdotdir/.zshenv`, not from rewriting commands: `session.start` points the process's `ZDOTDIR` there (keeping the person's value in `ZSH_SAFE_ZDOTDIR`), and that file hands `ZDOTDIR` back, sources the person's `.zshenv`, then runs `setopt nonomatch noequals`. Every zsh Claude Code starts reads it. Prefixing `setopt ...;` to the command was tried first and dropped: the permission rules see the rewritten command, so `Bash(echo:*)` stopped matching, and merging verdicts in `tool.check` could not tell an ask a PreToolUse hook of another plugin made from one the prefix caused.

`hooks/register.js` also has one `tool.call` hook, which runs the command unchanged and, when the result is an error saying `command not found: timeout`, appends the fix (the Bash tool's `timeout` parameter) to the result's `context`, which only the model reads. A lexical scan that denied `timeout` before the run was tried and dropped: it mistook variables, here-document lines and `case` patterns for commands.
